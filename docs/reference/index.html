udeep.mpl

src/udeep/mpl.py

matplotlib entry point: udeep.mpl.imshow / colorbar / savefig_hdr.

import udeep.mpl as hp
img = hp.imshow(ax, data, mode="extend", knee=240, stretch={"kind": "linear", "lo": -160, "hi": 1200},
                unit="HU", knee_rule="preset; top of the soft-tissue window", noise=("constant", 10.0))
hp.colorbar(img, ax=ax, label="HU")
hp.savefig_hdr(fig, "figure.jpg")                 # one file: the ordinary figure + a gain map
print(hp.caption(fig))                            # a caption generated from the declared mapping
hp.inline(fig)                                    # in a notebook: that file, shown in the cell's output

matplotlib only ever draws the fair SDR plot, so the figure, savefig PNG/PDF and the gain-map base are all the ordinary figure. savefig_hdr renders the figure four times: as it is; with each HDR layer scaled into range; and with the layers all black and then all white, which shows the pixels that an HDR layer alone makes. Only those pixels are lifted, and only where the scaled render is brighter. Axes, text and background stay at SDR white, and so does anything drawn over an image, such as a legend, with the image under it. The HDR render goes through 8-bit Agg, so gain above white is quantised to about headroom/255 of SDR white.

The headroom is fixed when the image is made (imshow(headroom=...)): the mapping, the colours and the declaration all follow from it, so a file cannot be saved at another.

Write the figure as a gain-map JPEG: the ordinary figure, plus gain on the HDR images only.

The file carries the profile's declared metadata (unit, mapping, knee and its rule, precision) unless metadata=False; without it the file does not conform to the profile.

The file's headroom is the one the images were made at (udeep.mpl.imshow's headroom=). headroom need not be given; a value that differs from the images' is refused, because the file would not be what it declares.

tight=True lays the figure out like savefig(bbox_inches="tight") -- expanding to take in labels outside the canvas -- and renders every pass that way, so the gain stays aligned with the base. The SDR figure this file's digest refers to is then fig.savefig(..., bbox_inches="tight", pad_inches=pad_inches), not a plain fig.savefig(...).

Before the file is written the gain map is decoded again and lowered wherever the figure would read above its brightest value (udeep.gainmap.write_gainmap_jpeg), which takes several coding passes on a coloured figure. gain_quality below 100 is unreliable with coloured maps (fire, ice), with this writer or any other: where one SDR channel is small each gain code is a large step. The passes may then not converge, and ValueError is raised and no file written rather than a file that reads over its headroom. Leave it at 100 unless the figure is grey.

udeep.view

src/udeep/view.py

The two presets of the UDeep Figure Profile (v0.3, section 13).

highlight -- a high, meaningful knee; sparse extremes go above SDR white. Isolated pixels above
             the knee are held at white so noise cannot sparkle: a derived mask (udeep.masks).
extend    -- the knee at the top of the main range; a second range of real structure goes above
             white. No area filter: thin real structure (e.g. bone cortex) must lift too.

Both keep the plot below the knee identical to the SDR plot clipped at the same white (the fair baseline), never lift masked pixels (saturation, blooming, clipping), and take the knee in data units. A missing knee falls back to a percentile and is flagged as exploratory.

The view holds three arrays the size of the image: the two renderings and the light. The ordinary full-range SDR plot is not kept (it was a third rendering, and nothing used it): it is `view.mapping.colours( view.mapping.position(data))` when wanted.

The renderings are float64 unless float32=True is asked for, which keeps them in half the memory (32 bytes a pixel held for the view, against 56). The mapping is worked out in float64 either way and each colour is rounded once as it is stored, so a float32 rendering is within one part in 10 million of the float64 one, far inside an 8-bit file's step; but it is not the same number, so the default stays float64.

The mapping is done by the Rust core wherever it is found (udeep.core), on every processor core, to within about one part in 10^12 of the reference. The reference is the NumPy code, which does it where the core is not found or has been turned off (udeep.core.enable(False)).

The mapping itself is a Mapping record (udeep.mapping) and is pointwise. This module applies it to an image in three steps: derive any mask the preset calls for, map every pixel, hold the masked ones.

udeep.mapping

src/udeep/mapping.py

The mapping from data to light and colour, as one record of parameters (design decision D3).

value x  ->  position t in [0, 1]  ->  light y, in multiples of SDR white  ->  linear RGB, same unit

A Mapping holds exactly what a file declares about that chain, under the same names as the udeep: metadata properties. Everything that computes with the mapping takes this record, so a figure can be rebuilt from its own metadata, and nothing can depend on a parameter the file does not record. The same record is meant to become the C struct of the native library and the uniform block of the shader.

Each method is a pure function of single values: no pixel looks at a neighbour (D1, D2). All are float64 and written against the Array API standard, so they run on any array library that follows it (D8, D22).

classMapping

The parameters of one mapping from data to light and colour, under the names a file declares them by.

udeep.cmap

src/udeep/cmap.py

y (multiples of SDR white) -> linear sRGB colour.

A colour map is a TABLE, and the table is its definition (design decision D9): two segments, light 0 to 1 and 1 to the reference headroom, each of NODES evenly spaced nodes holding linear RGB (BT.709 primaries, multiples of white, float32), with linear interpolation between nodes. cmap looks colours up in it.

cmap(y, name, headroom)    colours, from the table
table(name, headroom)      the Table: shipped for the registered headrooms (2, 4, 8, 16), built otherwise
search(y, name, headroom)  the generator that tables are made from (tools/make_tables.py); not for runtime use

A map's definition has a version, and a file names both ("fire/3"). Every version stays registered, so that a file made with an older one can always be read; new figures use the current one (VERSION). Each function takes version= for an older one.

How the generator builds a map, in Jzazbz: for y <= 1 the colour's lightness (Jz) is that of a grey of luminance y * top, where top is below 1, so SDR data never passes through white. (Its luminance is close to y * top but not equal to it: at y = 1, 0.85 for fire against a top of 0.8, and 0.78 for ice against 0.7.) For y > 1 luminance rises from top to headroom while chroma tapers to 0: extremes become white-hot, brighter than SDR white. Chroma is then reduced (fixed-step bisection) until the colour fits [0, 1] (y <= 1) or [0, headroom] (y > 1). Below white the map does not depend on the headroom; above white it does, which is why a table belongs to a (map, headroom) pair.

Version 1 measured chroma from az = bz = 0, which in Jzazbz is close to grey and not grey: with the chroma tapered to nothing, the top of a map was a faint tint that had then to be clipped to the headroom, so the last step of a map could fall in lightness. Its ice map also ran along the edge of the gamut near 15 % of white, where lightness dipped for red-green colour-vision deficiencies. Version 2 measures chroma from the (az, bz) of the grey of the same lightness, so that no chroma is exactly grey and the top is exactly white; and its ice map asks for less chroma at its second node (0.13 against 0.16), which keeps it off that edge. In version 2 lightness rises at every node of every shipped table, for normal vision and for each simulated deficiency (udeep.vision; tested).

Version 3 is version 2 with every value below FLOOR (1e-7 of white) set to zero. Where version 2 holds a channel at the edge of the gamut it leaves the small remainder of the arithmetic, a few hundred-millionths of white, and that remainder depends on which processor-specific routines NumPy and OpenBLAS choose: the generator did not give the same table on every machine (project/performance-scope.md, 4g). With the remainders removed it does, so a version-3 table can be checked by making it again. No colour moves by more than FLOOR.

udeep.gainmap

src/udeep/gainmap.py

Gain-map JPEG (Ultra HDR v1 layout, the model ISO 21496-1 standardises) for scientific plots.

The primary image is the ordinary SDR plot; a gain map records how much brighter each pixel is in the HDR plot. A display applies the gain in proportion to its own headroom (HDRCapacityMin..Max), so one file shows the SDR plot on SDR screens, part of the gain on a 2x panel, all of it at headroom and beyond -- a static, declared per-display fit.

Spec: developer.android.com/media/platform/hdr-image-format. Deliberate choices for plots: the gain map is full resolution and 3-channel (the spec recommends 1/4 size, which blurs sharp data into halos, and a luminance-only map cannot carry the colour change above white); JPEGs are 4:4:4 so thin lines and text keep their colour. Layout: primary [SOI, APP1 XMP container, APP2 MPF, ...] followed by the gain-map JPEG [SOI, APP1 XMP hdrgm, ...].

functionwrite_gainmap_jpeg

write_gainmap_jpeg(
    sdr,
    hdr,
    path,
    headroom: float,
    quality: int = 95,
    gain_quality: int = 100,
    description: bytes = b'',
    iso: bool = True,
) -> None

sdr: linear RGB in [0, 1] (the SDR plot); hdr: linear RGB in multiples of SDR white.

A pixel the figure does not lift (hdr no greater than sdr in all three channels) is stored with a gain of exactly 1, so GainMapMin is 0 and the gain map is flat wherever the figure is not lifted. No pixel is darkened: a channel that is lower in hdr than in the stored SDR plot keeps the SDR value.

Before the file is written its gain map is decoded again and the figure a reader would show is rebuilt; where that is brighter than the largest value in hdr the gain is lowered and the map coded again, until nothing is over. The cost is time (several coding passes on a coloured figure) and a top of the range that reads a little low. If it cannot be done the file is not written and ValueError is raised: a file is never written that reads above the brightest value it was given, on this module's reader.

The gain map is stored at gain_quality (default 100): its errors are exponentiated, so JPEG ringing at sharp gain edges (a colour bar beside a white background) otherwise pushes values past the headroom. Below 100 it is unreliable on coloured maps (fire, ice: where one SDR channel is small the gain range is wide and each code a large step, with this writer or any other): the passes may not converge, or gain may spread onto unlifted pixels, and the call then raises ValueError; a file that is written may still fail the validator's checks on its pixels. Leave it at 100 unless the figure is grey.

description is an extra rdf:Description for the primary image's XMP packet: the profile's declared metadata, from udeep.metadata.description. iso=True also writes the gain-map metadata in the binary form of ISO 21496-1, beside the Ultra HDR XMP, for decoders that read only that.

functionvalues_pq16

values_pq16(
    mapping: Mapping,
    light,
    sdr_white_nits: float = REF_WHITE_NITS,
    samples: int = 1 << 20,
) -> np.ndarray

The data values that a 16-bit PQ PNG's light stands for (light as udeep.read_png_pq gives it): the declared mapping turned back, through the file's own codes, whatever the colour map.

Each stored level is a run of data values that share one code in all three channels (data_steps_pq16). A pixel is given the middle of the run whose code it holds, and so comes back to within half that run's width, which is at most half of MaxDataStep. Near black PQ codes change faster than any even sampling can follow: there, where two neighbouring samples are more than one code apart in some channel, the gap between them is halved, and halved again, until no piece of it skips a code (at most REFINE_STEPS times). Where two neighbouring points differ, the first change of code between them is found to within a millionth of their spacing; if the code just past it is not yet the second point's, the next change is found the same way, and so on, so that a colour held between two channels' changes is a level of its own. A writer that rounds a sum of three products in a different order can leave a rare code one step from the reference's (udeep.core); a pixel whose code is in no run takes the nearest run that is a step away in each channel at most, and a pixel with none so near is not a colour of this mapping and is NaN.

tests/test_udeep_readback.py checks this against values found by walking out from each one in data space.

ValueError when two separate runs share one code: that code would not say which data value it stands for. It has not happened with any map tried (grey, fire and ice, linear over 0 to 4095 at a 4x headroom).

functionrounding_to_noise

rounding_to_noise(
    mapping: Mapping,
    noise: tuple,
    scaled_by: float | None = None,
    steps: tuple | None = None,
) -> dict | None

The data criterion (profile 7.2.1) for a file's stored levels, or None when the noise is unknown.

For a noise model, each level's rounding error (its width / sqrt(12)) is divided by the data's standard deviation at that level; the limit is K = 0.1. For a declared tolerance, the largest rounding error (half the width) is divided by the tolerance; the limit is 1.

The noise is taken at the point of each level where it is smallest, so a level meets the criterion only if all of it does. Poisson and relative noise grow away from zero, so that point is the one nearest zero, min(max(0, start), start + width): the end of the level nearer zero, or zero itself when the level contains it. At zero the noise is zero and the ratio infinite, so a range that reaches zero cannot meet the criterion (7.2.1). Constant noise and a tolerance are the same everywhere, and are reported at the middle of the level.

Returns the worst ratio (the first, if several levels share it), the data value where it was taken, the limit, whether the whole declared range meets it, and the fraction of the range that does not.

src/udeep/validate.py

print(report); report.ok

Two kinds of file are checked: the gain-map JPEG, which is always a rendering, and the 16-bit PQ PNG (udeep.export.write_png_pq), which may declare itself a data record. udeep.tone

src/udeep/tone.py

t -> y in multiples of SDR white (t is already log/asinh scaled).

y = t / knee                          for t <= knee   (SDR: 0 .. 1)
y = cubic Hermite from 1 to headroom  for t >  knee   (HDR: 1 .. headroom)

The shoulder starts with the slope of the SDR part (C1: no kink, so no Mach band at the knee) and ends at exit_slope times its secant slope. The default, 1, is the **declared mapping** of the profile (v0.3, 6.3): strictly increasing, so every light level maps back to one data value. With entry slope a and exit slope 1 (in units of the secant) the slope is (3a-3)u^2 + (4-4a)u + a, never below min(a, (4-a)/3) of the secant. exit_slope=0 ends flat at headroom, the roll-off of ITU-R BT.2390's EETF: use it only for display rendering, because it squeezes the top of the data range into the last few percent of light, where it cannot be recovered.

If 1/knee exceeds three times the secant slope, the entry slope is capped there (Fritsch-Carlson: entry and exit slopes both within [0, 3] secants keep a cubic Hermite monotone), at the cost of C1 in that corner case.

knee = 1 gives the full-range SDR plot (y = t); headroom = 1 with knee < 1 gives SDR clipped at the same white -- the fair baseline an HDR rendering must match below white.

src/udeep/core.py

The Rust core, used from Python wherever it is found.

import udeep.core
udeep.core.enabled()           # True when the core was found and has not been turned off
udeep.core.enable(False)       # use the NumPy and Pillow code instead, from here on

The core (core/, a Rust library with a C interface) is used wherever it is found: it maps and colours an image on every processor core at once (60 to 250 megapixels a second on the development machine against NumPy's 8 to 12, project/performance-scope.md 4d), and it writes and reads gain-map JPEGs. The two are held to the same golden vectors, and that is the sense in which they are the same: they agree to about one part in 10^12 in the mapping (their logarithms and hyperbolic sines come from different libraries), which is far inside any file's precision but can turn an 8-bit code the other way at a few pixels, and so give a figure another SDR digest. The two JPEG decoders also differ by a code or two at some pixels: a file is held within its headroom exactly on the decoder its writer used, so write and read with the same one.

The library is looked for at ENV["UDEEP_CORE_LIB"], then beside this module (udeep/_lib, where a packaged build would put it), then in core/target/release of a source checkout (cargo build --release in core/).

udeep.gpu

src/udeep/gpu.py

The mapping on a GPU: the reference shader (shaders/mapping.wgsl) and a way to run it and read it back.

uniform_block(mapping)      the shader's parameter block, worked out in float64 and packed as float32
run(mapping, x)             position, light, fair SDR light and colours for an array of values, from the GPU
expected_error(mapping)     how far float32 can be expected to fall from the reference, in units of the tolerances
check(mapping)              ValueError if that is more than a tolerance, or a number does not fit float32

run needs the optional wgpu package (WebGPU for Python, on Vulkan, Metal or DirectX). It exists to hold the shader to the golden vectors and to map large batches; a viewer uses the shader's three functions in its own render pipeline instead. The GPU renders and the CPU reference defines (design decision D15): given the same float32 values, results agree with the float64 reference to 2e-6 x (1 + |value|) in position and light, and to 1e-5 x (1 + |value|) in colour (D8), not exactly. Where float32 cannot do that, uniform_block and run raise ValueError: they do not return a worse answer.

Colour has the wider tolerance because it is judged by what reaches a screen, and because a steep stretch of a colour-map table multiplies the light's error: fire/1 at headroom 2 has one step, seventeen nodes below its top, where blue climbs 19 units per unit of light. 1e-5 is about a fiftieth of half a 10-bit code (0.5 / 1023 = 4.9e-4); the largest difference measured in any accepted mapping is 0.007 of an 8-bit code.

What float32 can hold

The ends of the range and the offset need not be float32 numbers: 273.15..303.15 or 20000.1..20001.1 are held as well as 0..1, because every constant that is subtracted is passed as a pair of float32 (uniform_block). Three things remain, and check refuses each. The positions below are of the knee in the range, for the profile's reference form above the knee (exit slope 1), and are where the rule draws the line, not where the shader fails: run regardless, a mapping just past one of them measured about half its tolerance.

1. A number that does not fit a float32 at all: a size above about 3.4e38, or below about 1.2e-38 and not zero. That covers the ends of the range, its width and the reciprocal of its width, and for a log stretch the ratio of the ends. 2. log and asinh. The function's result is itself a float32, so the position carries a rounding that does not shrink with the range: about 2.2e-7 for a log, and for an asinh between 2.6e-7 of the stretched value (where that is below 1) and 1e-7 of it (above about 4), each divided by the stretched span. A log range must therefore span a ratio of 1.12 at the very least, and more once the curve multiplies the error: with the knee in the middle, 1.25 at headroom 2, 1.4 at 4 and 7.4 at 16. An asinh range must span a ratio of 1.5 where its low end is no more than the width, 1.7 where it is ten widths and 2.1 where it is a hundred (knee in the middle, headroom 4). A knee low in a log or a narrow asinh range is steep enough to break the tolerance: below position 0.012 of a log range of four decades. A linear stretch has no such limit: its error is a fraction of the position. 3. Steepness. The light is out by the position's error times the slope of the curve, and a colour by the light's error times the slope of the colour-map table. So a knee near the top is refused, sooner with more headroom. With a grey map the knee may be as high as

   headroom                              2       4       8       16
   linear                                0.955   0.905   0.84    0.75
   log, four decades                     0.93    0.845   0.745   0.62
   asinh, 0 to 200 widths                0.935   0.85    0.755   0.63

The shipped colour maps, fire/1 and ice/1, are held at every shipped headroom (1, 2, 4, 8 and 16): none is refused outright. At headrooms 4, 8 and 16 their limits are those of the grey map, and at headroom 1 there is none. At headroom 2 the table is steep enough to bring the limit down:

   headroom 2                            linear  log     asinh
   ice/1                                 0.95    0.92    0.92
   fire/1                                0.85    0.75    0.76
   fire/1, exit slope 2                  0.71    0.51    0.53
   fire/1, exit slope 3                  0.565   0.27    0.30

With any colour map, a headroom between 1 and about 1.03 squeezes the whole upper table into a sliver of light, and is refused. A headroom of exactly 1, and a grey map at any headroom, are not.

expected_error is the rule itself: it follows those errors through the chain and check refuses when any is above 1. Its nine constants are measured, on an NVIDIA RTX 5070 Ti through Vulkan, not derived, and other hardware may differ: the tests measure again on whatever GPU they find. On 1800 mappings drawn at random (linear, log and asinh; grey, fire and ice; headrooms 1 to 16) and sampled closely at both ends and just above the knee, 1433 were let through and none of those was out: the largest error was 0.79 of its tolerance (light) and 0.54 (colour), the median 0.17. Of the 367 refused, 203 were out when run regardless and 164 were not: the rule errs towards refusing, and most of all for colour, where it adds up the worst each step can do. Of 20 mappings refused for their colours alone, 3 were out. Two closer looks at the colour limit found nothing out either: 250 accepted mappings whose expected colour error was above 0.6 measured 0.65 at most, and 122 accepted with a colour map at a headroom between 1.005 and 1.1 measured 0.58 at most.

functionuniform_block

uniform_block(mapping: Mapping) -> bytes

The shader's Mapping uniform: 64 bytes, twelve float32 then four uint32, little-endian, in the order of FIELDS (the shader file documents each). Everything is worked out in float64 first.

A number that is subtracted comes as a pair, _hi and _lo: the nearest float32, and what is left of the float64 number after it, already multiplied by the factor the shader applies between the two subtractions. Raises ValueError for a mapping the shader cannot hold to the tolerance (check).

functionexpected_error

expected_error(mapping: Mapping) -> dict

How far the shader's float32 answers can be expected to lie from the float64 reference, for position, light and colours, each as a multiple of its own tolerance: 2e-6 x (1 + |value|) for position and light (TOLERANCE), 1e-5 x (1 + |value|) for colours (COLOUR_TOLERANCE). Each is the largest over the range.

It follows the error through the chain at GRID positions. The position is out by a fraction of itself (POSITION_RELATIVE) and, for log and asinh, by the rounding of the function's argument and of its own float32 result, divided by the stretched span. The light is out by that times the slope of the curve, plus the rounding of the curve's own arithmetic. A colour is out by the light's error at the same place times the slope of the colour-map table there, plus the rounding of the interpolation. The constants are measured, not derived: see the module docstring.

functioncheck

check(mapping: Mapping) -> None

Raise ValueError unless the shader can hold this mapping to its tolerances: every number it needs fits a float32, and no part of expected_error is above 1 (position and light in units of TOLERANCE, colours in units of COLOUR_TOLERANCE). The module docstring says what that rules out.

udeep.golden

src/udeep/golden.py

Golden vectors: the contract every implementation must reproduce (design decision D14).

python -m udeep.golden        # rewrite golden.json after a deliberate change

golden.json is language-neutral. Each case has a kind (what to compute), args, the expected out, and how closely a result must agree: tol = {"rel", "abs"} for numbers (|got - want| <= abs + rel * |want|), or exact for text, digests and bytes. NaN is written as null. The tolerances are the written ones of decision D8: tight where an implementation in float64 must agree with the reference, looser where float32 tables or GPU arithmetic are involved.

Kinds: scale, tone, pq_encode, srgb_oetf, cmap (a table lookup), table (a shipped table's digest), mapping (a parameter record: position, light, fair SDR light, the inverse, colours), levels (stored levels and the data criterion, for the 8-bit gain-map path), levels_pq16 (the same for a 16-bit PQ PNG), mask_isolated, digest_data, digest_pixels, xmp (a declaration's serialised form), caption, iso21496 (the gain-map metadata block's bytes).

A levels_pq16 case is a levels case for a 16-bit PQ PNG with white at white_nits (203 cd/m2, profile 9.1.1): one code for each colour, no split at the knee. Its mappings are the grey forms of the mapping records. Sixteen-bit codes are fine enough that a float32 colour table, which ports may interpolate in other arithmetic, would move codes that sit near a rounding tie; with grey the case pins the PQ path itself, and the colours are pinned by the mapping cases. Each case is checked, when it is made, to keep every code under a relative change of 1e-12 in the light.

A levels case gives the noise as [model, parameter]. Its rounding_to_noise is the worst ratio as a file states it, no larger than 1e9: the ratio is unbounded where the noise reaches zero, and JSON has no infinity. at, the data value where the worst ratio was taken, is given for poisson and relative noise, and only where one level is clearly the worst. Elsewhere (constant noise, a tolerance, relative noise on a log stretch) many levels share the worst ratio to within rounding, so which of them is found is not part of the contract and at is left out.

Differences between a result and the expected output, under the case's own tolerance; empty if none.
